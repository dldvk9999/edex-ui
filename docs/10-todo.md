## 10.0 Recently Fixed (this pass)

| Bug | Fix |
|---|---|
| ~~"Preferences" menu item does nothing when clicked~~ | Fixed — `registerApplicationMenu()` in `src/_boot.js` now sets a real `Menu.setApplicationMenu()` (macOS app-menu item + Windows/Linux File-menu item, both `CmdOrCtrl+,`) that sends an `open-settings` IPC message to the renderer, which calls the existing `window.openSettings()`. |
| ~~Slight upward shift right after the "eDEX-UI" boot title box appears~~ | Fixed — `displayTitleScreen()` in `src/_renderer.js` now reserves the title's full 5px border on all four sides (three sides transparent) starting from the first inline-style step, so the following step only changes border-*color*, never border-*width/sides*. Removes the layout height jump previously caused by a top border appearing out of nowhere. |
| ~~On-screen keyboard show/hide toggle~~ | Done — a `⌨` button fixed at the bottom of the screen (always visible/clickable regardless of keyboard state, unlike a control placed inside the keyboard itself) and a new `TOGGLE_KEYBOARD` app shortcut (default `Ctrl+Shift+B`) both call `window.toggleKeyboard()` in `src/_renderer.js`. Toggling adds/removes a new `kb_collapsed` CSS class (opacity/transform slide-down, independent of the boot-only, forward-only `animation_state_1`/`2` reveal classes - see `docs/02-architecture.md`), then applies `display:none` once the transition finishes so the keyboard's flex-layout space is actually reclaimed rather than just left invisible. Persisted via a new `settings.keyboardHidden` field, so a hidden keyboard stays hidden across restarts (`initUI()` skips the reveal animation/sound entirely in that case, rather than playing it and immediately hiding it again). |
| ~~Accessibility — remaining gaps (file browser, on-screen keyboard, fuzzy finder, process list)~~ | Done - the modules called out by the first pass now have real semantics. **File browser** (`filesystem.class.js`): `#fs_disp_container` is a `role="listbox"` of `role="option"` items with a roving-tabindex Left/Right/Up/Down/Home/End/Enter/Space handler (linear, not true 2D grid-nav - the grid's column count is width-dependent via CSS `repeat(auto-fill, ...)`, so linear DOM-order traversal is the pragmatic choice); the disk-view "EXIT DISPLAY" bar gets `role="button"`/`tabindex` only while it's actually clickable. **On-screen keyboard** (`keyboard.class.js`): every key gets `role="button"` and a computed `aria-label` (not made `tabindex`-focusable on purpose - operated by pointer/touch/switch-scanning tools that read the accessibility tree's role/label directly; adding tabindex to ~60 keys would turn the app into one long tab trap); the container gets `role="group"` + a label. **Fuzzy finder** (`fuzzyFinder.class.js`): already had full keyboard operation (arrows/Enter), now also has real combobox/listbox ARIA (`role="combobox"` + `aria-activedescendant` on the input, `role="listbox"`/`"option"`/`aria-selected` on the results) instead of a CSS class alone; selection-sync was deduplicated into one `_selectMatch()` shared by the keydown handler and each result's click, which incidentally fixed a dormant bug where the "No results" message was immediately overwritten by a blank list right after being set. **Process list** (`toplist.class.js`): the mini sidebar widget is a real `role="button"` (`tabindex`, `aria-label`, Enter/Space); the full modal's sortable column headers are `role="columnheader"` with `aria-sort` kept in sync and Enter/Space activation, not click-only. No actual screen-reader testing (VoiceOver/NVDA) has been done, consistent with the first pass. |
| ~~Theme editor GUI~~ | Done — `window.openThemeEditor()` in `src/_renderer.js`, reachable via Settings > theme > "Edit Theme" or the new `THEME_EDITOR` app shortcut (default `Ctrl+Shift+T`). Color pickers (`<input type="color">`, via the `color` npm package already used elsewhere in the codebase for hex/rgb conversion) and font dropdowns (limited to the 4 bundled fonts - see `docs/05-design-theme.md` 5.1 - since arbitrary font names have no matching `.woff2` to load) cover the fields most themes actually differ on. Every change live-previews instantly through the same `window._loadTheme()` the boot sequence and theme hotswitch already use - no reload while editing, only expected on next launch after Save. Editing operates on a full clone of the source theme's JSON (fields the editor doesn't expose - `cursorStyle`, `colorFilter`, `injectCSS`, `terminal.selection`'s alpha - are preserved as-is, not dropped) and never mutates the `require()`-cached object `window.theme` is built from. Closing without saving restores whatever theme was actually applied before the editor opened. Save writes to a user-chosen name (sanitized against path traversal, since it's a text field feeding a filesystem write) under the themes folder, as a new file or overwriting an existing one. |
| ~~Program-launcher tab~~ | Done, with one deliberate scope change from the original request: `src/classes/appLauncher.class.js` (new, `AppLauncher`) is a standalone on-demand modal (same pattern as `FuzzyFinder`) rather than a tab that only appears when the on-screen keyboard is collapsed, as originally requested - that coupling would've meant keyboard-attached desktop users who never hide the keyboard could never reach it. Bound to a new `LAUNCH_APP` shortcut (default `Ctrl+Shift+A`). Discovery has no shared cross-platform mechanism, so each OS gets its own strategy: Windows walks the system + per-user Start Menu `Programs` folders for `.lnk` files (launched via `electron.shell.openPath()` without parsing their target - Windows can execute a `.lnk` directly); macOS lists top-level `*.app` bundles under `/Applications` and `~/Applications`; Linux (and other XDG-compliant platforms) parses `.desktop` entries under the standard system/user application directories, skipping `NoDisplay=true` ones. Search/select/launch reuses the same keyboard-nav + combobox/listbox ARIA pattern as the fuzzy finder (10.0's a11y pass) for consistency, down to a shared `_selectMatch()`-style helper. |
| ~~Plugin / external module system~~ | Done - full writeup in the new `docs/11-plugins.md`. Users drop a folder (`plugin.json` manifest + a `main.js` exporting `activate()`) into `userData/plugins`; `window._loadPlugins()` in `src/_renderer.js` loads each one via `require()` at the end of `initUI()`, after every core global (`window.mods`, `window.term`, `window.settings`, etc.) a plugin might want already exists. **Deliberately not sandboxed** - the app already runs with `nodeIntegration: true`/`contextIsolation: false` (`docs/07-security.md`), so a plugin gets exactly the trust/access any `src/classes/*.class.js` file already has; since only plugins the user has explicitly placed locally are ever loaded (never anything remote), this introduces no new attack surface beyond what already exists, and is documented as an explicit, deliberate trust-model decision rather than an oversight - see `docs/11-plugins.md` 11.1. A single throwing/broken plugin is caught and logged, not allowed to take the app down, same defensive posture as `registerKeyboardShortcuts`' per-entry try/catch. Unlike the `themes`/`keyboards`/`fonts` folders (re-synced every launch), `userData/plugins` is created once and never touched again, so an app update can never silently clobber an installed plugin; a disabled-by-default example plugin + README ship in it on first creation. |

## 10.3 Suggested Starting Points

Everything except split panes is now done (see 10.0 above), including the program launcher (built as a standalone modal rather than coupled to the keyboard-collapse state it was originally requested alongside) and the plugin system (deliberately unsandboxed - see docs/11-plugins.md 11.1 for why that's a considered decision, not an oversight). Split panes is what's left: a new layout engine, genuinely the largest remaining undertaking on this list.
