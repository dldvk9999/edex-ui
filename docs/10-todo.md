# 10. Feature TODO / Proposals

A list of features worth considering for future work, gathered by researching community requests (GitHub issues/discussions on the archived upstream repo) and by direct analysis of the current codebase.

## 10.0 Completed

| Feature | Notes |
|---|---|
| ~~In-terminal search (Find)~~ | Done — `xterm-addon-search` wired into the `Terminal` client class, bound to `Ctrl+Shift+G` via a new `TerminalSearch` modal. See `src/classes/terminalSearch.class.js`. |
| ~~Tab renaming~~ | Done — double-click a shell tab to give it a custom name via a rename modal (`window.renameShellTab`/`window.tabNames` in `src/_renderer.js`). Custom names survive process/cwd changes but are **not persisted across app restarts** — see 10.2 below, this was split out as a separate follow-up rather than done as part of the same change. |
| ~~Session/layout save & restore~~ | Done — opt-in via the new `restoreSession` setting (off by default, toggleable from the in-app Settings editor or by hand-editing `settings.json`). On every tab open/close/rename and on unload, the renderer writes `lastSession.json` (main tab cwd, each open extra tab's cwd + custom name, and the focused tab). On next launch, if enabled: `_boot.js` reads it before spawning the main tty to restore its cwd, and `_renderer.js` recreates extra tabs (1-4) at their saved cwd/name via an extended `ttyspawn` IPC call (now accepts an optional target cwd, falling back to the pre-existing "inherit main tab's cwd" behavior when omitted). Custom tab names (10.0 above) are restored as part of this. |
| ~~Editable shortcuts UI~~ | Done — the shortcuts help screen (`Ctrl+Shift+K`, `window.openShortcutsHelp` in `src/_renderer.js`) is now a live editor instead of a read-only listing. App-type (built-in action) rows allow editing trigger + enabled; custom shell-command rows are fully editable and can be added/removed via `window.addCustomShortcutRow`. "Save to Disk" (`window.saveShortcuts`) rewrites `shortcuts.json` and re-registers shortcuts immediately (`globalShortcut.unregisterAll()` + `registerKeyboardShortcuts()`), no reload needed. `registerKeyboardShortcuts` also gained a try/catch per entry so one malformed accelerator (now user-typable, previously only ever hand-edited by technical users) can't take the rest down with it. |
| ~~Tab reordering~~ | Done — extra tabs (slots 1-4) can be drag-and-dropped into a new order via native HTML5 drag & drop (`window.tabDragStart`/`tabDragOver`/`tabDrop`/`tabDragEnd`, `window.renderTabOrder` in `src/_renderer.js`). The main tab (slot 0) is pinned first and isn't reorderable - this sidestepped most of the port/index coupling risk called out below, since slot *identity* (port/process/name) never moves, only which DOM position it renders at. `window.tabOrder` (an array of slot numbers, persisted as part of `lastSession.json` when `restoreSession` is on) tracks visual order; `focusShellTab`'s active-tab highlighting was switched from `nth-child` CSS selectors (which assumed DOM position === slot number) to ID-based lookups so it stays correct regardless of reordering. `TAB_1`..`TAB_5`/`NEXT_TAB`/`PREVIOUS_TAB` shortcuts now resolve *visual position* to slot through `window.tabOrder` instead of assuming a fixed number-to-slot mapping. |
| ~~SSH profile manager~~ | Done — new `Ctrl+Shift+O` opens `window.openSSHProfiles`, an editable table of saved profiles (name/host/port/username/identity file, stored in `sshProfiles.json`) with a native file picker for the identity file (`window.browseSSHIdentityFile`). "Connect" builds an `ssh` command line, opens it in a free extra tab (spawning one if needed, named after the profile) via the new generic `window.runShellCommand` helper, and falls back to running in the currently focused tab if all 4 are already open. Writing to a *freshly spawned* tab needed a new `window._waitForSocketOpen` helper - `Terminal.write()`/`writelr()` call `this.socket.send()` directly, which throws if the websocket isn't `OPEN` yet, and `spawnShellTab`'s promise had been resolving right after construction, well before the handshake completes. |
| ~~More popular color-scheme themes (Dracula)~~ | Done — added `src/assets/themes/dracula.json` using the standard Dracula palette (`#282a36` background, `#bd93f9` accent). No code changes needed: themes are discovered dynamically at runtime (`fs.readdirSync(themesDir)` in `src/_renderer.js`, copied from `src/assets/themes` on first launch by `src/_boot.js`), so a new theme is just a JSON file matching the schema in `docs/05-design-theme.md`. |
| ~~Network interface selector dropdown~~ | Turns out already done, this list entry was stale. `netstat.class.js`'s `updateInfo()` already prefers `window.settings.iface` when set (falling back to auto-detection). The Settings editor (`window.openSettings` in `src/_renderer.js`) already renders an `iface` `<select>` populated from `window.si.networkInterfaces()`. Traced via `git log -S "settingsEditor-iface"` to `b69f348 :sparkles: Better netIface chooser & override option`, which predates this fork — it shipped upstream, just after issue #403 was filed. No code change made; removed the item from 10.1 and documented the `iface` setting in `docs/04-features.md` since it wasn't mentioned anywhere before. |
| ~~Volume control module~~ | Done — `src/classes/volumeControl.class.js`, a small widget next to the clock. macOS via `osascript`, Linux via `pactl` (falls back to `amixer` if pulse/pipewire's pactl isn't present), Windows via a PowerShell + C# helper that drives the Core Audio `IAudioEndpointVolume` COM interface directly (there's no volume CLI on Windows). Slider input is debounced 120ms so dragging doesn't spawn a subprocess per pixel; after 3 consecutive failed get/set calls the widget disables itself and shows "N/A" instead of erroring forever (recovers automatically if a later poll succeeds, e.g. PulseAudio restarting). **Windows path is unverified** - the interface/GUID layout was cross-checked against Microsoft's `endpointvolume.h` docs and a community-verified reference script, but this fork's dev environment is Linux, so it has not actually been run on Windows. Please test and report issues. |
| ~~Lock screen module~~ | Done — `src/classes/lockscreen.class.js`, triggered by `Ctrl+Shift+Z` (`L` was already taken by `FS_LIST_VIEW`). Full-screen password overlay; on unlock failure the panel shakes and, after 3 failed attempts, a pulsing red warning glow + alarm sound kick in (`window.audioManager.alarm`). Password set via a new `lockPassword` field in the Settings editor - stored as a PBKDF2 (100k iterations, SHA-256) hash + random salt in `settings.json`, never plaintext (`LockScreen.hashPassword()`/`attemptUnlock()`, using `crypto.timingSafeEqual` for the comparison). `lock()` no-ops with a warning modal if no password has been set yet, rather than showing a screen anyone can bypass by pressing Enter. `useAppShortcut` gained a guard that blocks every other global shortcut while locked (tab switching, settings, dev tools, etc.) - global shortcuts are OS-level accelerators that bypass DOM focus entirely, so without this the overlay alone wouldn't have stopped them. **This is a privacy screen, not a real access-control boundary** - see the new note in `docs/07-security.md` explaining why, given this app's `nodeIntegration`/`contextIsolation` posture. |

## 10.3 Known Bugs (User-Reported)

Investigated by static code review only (no hands-on repro on an actual build in this pass - noted per item where that matters).

| Bug | Root cause & impact | Suggested fix | Effort |
|---|---|---|---|
| **"Preferences" menu item does nothing when clicked** | No file in this codebase defines a `Menu`/`Menu.setApplicationMenu()` at all (confirmed via full-source search) - `_boot.js` never calls it, so Electron falls back to its own built-in default application menu. That default template, verified directly against Electron 12's own source (`lib/browser/default-menu.ts` + `menu-item-roles.ts` at the `v12.0.0` tag), is `[appMenu, fileMenu, editMenu, viewMenu, windowMenu, help]` with `appMenu` = About/Services/Hide/Hide Others/Unhide/Quit - **no `Preferences` role exists anywhere in it, on any platform.** The most likely explanation is a macOS-specific convention: Cocoa/AppKit apps commonly get a "Preferences…"/"Settings…" item surfaced in their app menu as standard OS boilerplate even when the app's own menu template doesn't request one (multiple third-party sources describe this as unremovable), and since eDEX-UI never wires anything to it, clicking does nothing. **Unconfirmed - needs a report of which OS and exactly where ("Preferences" in the macOS top menu bar? A `File`/`Edit`/etc. submenu on Windows/Linux? Somewhere else?) to pin down for certain**, since this couldn't be reproduced through static review alone (no GUI in this environment). Impact: cosmetic/confusing (a menu item that looks broken), not a functional blocker; likely macOS-only given the Windows/Linux default menu items (`File`, `Edit`, `View`, `Window`, `Help`) don't literally say "Preferences" per the same source check. | Define a real `Menu.setApplicationMenu()` in `_boot.js` with an explicit `Preferences` item (`accelerator: "CmdOrCtrl+,"`) that opens the app's *existing* settings UI (`window.openSettings()`, added when the in-app Settings editor was documented - see 10.0) via IPC/`webContents.send`. Fixes the dead click regardless of the exact OS mechanism, and is a small, self-contained addition since the settings UI itself already exists. | Low |
| **Slight upward shift right after the "eDEX-UI" boot title box appears** | `displayTitleScreen()` in `src/_renderer.js` drives the boot title's visual states by calling `title.setAttribute("style", "...")` with a **complete replacement string** at each step, rather than changing only the properties that need to change. Sequence: (1) CSS gives `section#boot_screen h1` a `border-bottom: 0.46vh` only (no top/left/right border) while it fades in; (2) inline style is replaced with `background-color: ...; border-bottom: 5px solid ...` (still bottom-only, ~same size, but the background-color set here gets silently dropped again at the next step since step (3) doesn't re-specify it); (3) inline style is replaced again with `border: 5px solid ...` - **now adding a top border (and left/right) that didn't exist in any prior state.** `section#boot_screen h1` has no `box-sizing: border-box` (checked - not set globally or on this rule anywhere in `src/assets/css/`), so in the default `content-box` model this newly-added top border increases the element's total rendered height. Since the element sits in a flex-centered container (`section#boot_screen.center { align-items: center; }`), a height increase concentrated on one side (top, since bottom already had ~5px) recentres the box - its top edge moves up by roughly half the newly-added border width, its bottom edge moves down by the same amount. This is a real Cumulative-Layout-Shift-style bug, code-verified, not just a timing/animation-easing illusion. Impact: cosmetic-only, boot-intro-only (skipped entirely if `--nointro`/`settings.nointro` is set), a few pixels for well under a second - low severity but a legitimate, fixable bug, not a subjective nitpick. | Give `section#boot_screen h1` `box-sizing: border-box` (so later border changes redistribute space inside the already-reserved box instead of growing it), and/or reserve the full 4-side border width from the very first frame using a *transparent* border (`border: 5px solid transparent`) that only changes *color* in later steps rather than *width/sides*, so total box dimensions never change during the sequence - the standard technique for avoiding this class of shift. | Low |

## 10.4 User-Requested Features (Not Yet Scoped)

| Feature | Description | Effort |
|---|---|---|
| **On-screen keyboard show/hide toggle** | There is currently **no way to hide the on-screen keyboard at all** after boot - `classes/keyboard.class.js`'s `attach()`/`detach()` only gate whether keystrokes route to the terminal (`this.linkedToTerm`), not visibility, and the `animation_state_1`/`animation_state_2` CSS classes in `keyboard.css` are only ever applied once, during the boot entrance animation (`src/_renderer.js` ~line 445-458) - there's no button or persistent toggle anywhere in the current code. Requested: a button that slides the keyboard up from the bottom edge when opened (and presumably back down when closed). This is a genuinely new control, not a bug fix. | Low-Medium (a toggle button + a CSS transform transition reusing the existing slide-in mechanics, optionally persisted like other UI state via `settings.json`) |
| **Program-launcher tab shown when the keyboard is collapsed** | Requested alongside the toggle above: when the on-screen keyboard is hidden, show a tab in its place that launches an installed program (one tab/program for a first version). This is a materially different, much bigger piece of work than the toggle itself - it needs **cross-platform installed-application discovery**, which has no shared mechanism (Windows: Start Menu shortcuts/registry, macOS: scanning `/Applications` for `.app` bundles, Linux: parsing `.desktop` files under `/usr/share/applications` and similar) before a single `shell.openPath()`/`child_process.spawn()` call can actually launch anything. Worth confirming intent before scoping further - pairing a program launcher specifically with the keyboard-collapse state is an unusual coupling (why not a standalone launcher, reachable independent of keyboard visibility?) - noted here rather than assumed. | High (new OS-integration surface, one code path per platform, before any UI work even starts) |

## 10.5 Building on the Existing CI/Build Pipeline

- `updateChecker.class.js` only polls GitHub Releases to *notify* about new versions — it doesn't actually download/apply updates in-app. Since the project already uses `electron-builder`, wiring in `electron-updater` (same ecosystem) for real auto-update would be a relatively low-friction addition. **Update:** the CI now actually publishes built binaries to GitHub Releases on a tag push (`--publish`, see `docs/06-build-and-deployment.md` 6.5) - this was a prerequisite (`electron-updater` needs published release assets to check against), not the `electron-updater` integration itself, which is still not done.

## 10.6 Suggested Starting Points

All low/medium effort items from this list are now done (see 10.0 above), plus a first pass at accessibility. What's left - split panes, the remaining accessibility gaps (file browser, on-screen keyboard, smaller modules - see 10.2), the plugin/module system, the two newly-reported bugs (10.3, both Low effort - good next pick), the user-requested keyboard/launcher features (10.4), and full in-app auto-update (10.5) - are each either High effort (new layout engine, real architecture change, cross-platform app discovery) or a bigger cross-cutting undertaking, except the two bugs which are small and just haven't been picked up yet.
