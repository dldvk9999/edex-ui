# 7. Security Notes

- **CSWSH vulnerability (patched)**: the terminal websocket server originally did not validate the Origin header, allowing a malicious website — via a user's browser — to inject arbitrary commands into the local shell (`GHSA-q8xc-f2wf-ffh9`). Patched by having `verifyClient` only allow connections with no Origin header or an Origin of `file://`.
- **`nodeIntegration: true` + `contextIsolation: false`**: the renderer has direct access to Node APIs, which inherently widens the attack surface — if the renderer were ever to load arbitrary remote content, that would lead directly to RCE. `will-navigate`/`new-window` handlers block loading external URLs in-app, but the underlying architecture is fundamentally different from the isolated contextBridge pattern recommended by modern Electron security guidance. Because of this, **any DOM XSS anywhere in the renderer is equivalent to full local code execution** — this made the innerHTML/inline-onclick findings below unusually severe compared to a typical web app.
- A **`SECURITY.md`** file exists in the repository root, documenting the vulnerability-reporting process.

## 7.1 Findings from a full codebase security review (patched)

- **Toplist process names rendered unescaped** (`toplist.class.js`): process names from `systeminformation`'s process list were interpolated into `innerHTML` with no escaping. Since a local process can freely set its own name/argv[0], a maliciously-named process being merely *visible* in the (auto-refreshing, no click required) process list module was enough to execute arbitrary JS — and therefore arbitrary Node code. Fixed by routing all process fields through the existing `window._escapeHtml()` helper (which was already used elsewhere but not here).
- **Text file viewer's `<textarea>` content unescaped** (`filesystem.class.js`): opening any UTF-8 text file rendered its raw content inside a `<textarea>` without escaping. A file containing a literal `</textarea>` would break out of the textarea and let the rest of its content be parsed as live HTML/JS. Fixed by HTML-escaping the file content before interpolation (safe for `<textarea>` specifically, since browsers decode entities back to the original text for its `.value`).
- **HTML-escaping used in the wrong context for inline `onclick` JS strings** (`filesystem.class.js`): theme/keyboard-layout file names, and disk/USB mount paths (which on Linux commonly *include* the volume label), were embedded directly into `onclick='...("...")'` handlers. `window._escapeHtml()` alone does not protect this context, because browsers HTML-decode attribute values *before* treating them as JS source — so an HTML-escaped quote can still break out of the JS string at click time. Fixed by switching these cases to the same index-based array lookup pattern (`fsDisp.cwd[blockIndex]...`) already used elsewhere in the file, which avoids ever concatenating untrusted strings into the handler's JS source at all. Also added a `window._escapeJsString()` helper for the remaining case (`writeFile`'s path argument) that still needed a literal string embedded in an inline handler. As a side fix, `FilesystemDisplay.render()` wasn't keeping `this.cwd` in sync while showing the disk list, which this change also corrected (a latent, unrelated correctness bug that the fix depended on).
- **`pdfjs-dist@2.11.338` — CVE-2024-4367 (GHSA-wgrm-67xf-hhpq, "High")**: PDF.js executes attacker-controlled JS from a malicious PDF via `eval()` when `isEvalSupported` is left at its default (`true`). The real fix ships in `pdfjs-dist>=4.2.67`, which requires Node >=18 — not available under this project's Electron 12 runtime. Applied the vendor-documented workaround instead: `docReader.class.js` now explicitly passes `isEvalSupported: false` to `pdfjsLib.getDocument()`.
- **`systeminformation@5.9.7` — multiple OS command-injection CVEs**, several in functions this app actually calls on every run (`networkInterfaces()`, `fsSize()`). Upgraded to `^5.33.1` (same major version, no known breaking API changes for the functions used here).
- **`ws`, `nanoid`, `smoothie`** — bumped to their latest patched versions (`^7.5.13`, `^3.3.18`, `^1.36.1` respectively) to close DoS/predictability/XSS advisories. `ws` is notable since it's the same library the CSWSH terminal websocket server runs on.
- **Keyboard key labels rendered unescaped** (`keyboard.class.js`): key label fields (`name`, `shift_name`, `alt_name`, etc.) from a keyboard layout JSON were interpolated into `innerHTML` unescaped. Same trust class as themes (bundled by default, but the app supports dropping in custom layout files) — fixed defensively with `window._escapeHtml()`.
- **`codeql-analysis.yml` used deprecated action versions** (`actions/checkout@v2`, `github/codeql-action/*@v1`) — not a vulnerability by itself, but left unaddressed the security scanner itself could silently stop running once GitHub fully sunsets those versions, losing future coverage. Bumped to `actions/checkout@v4` and `github/codeql-action/*@v3`.
- **Reviewed and found no issues**: the GitHub Actions workflows don't interpolate untrusted PR-controlled context values (title, branch name, commit message) directly into `run:` shell steps — the classic "Actions script injection" pattern. `ui.html`'s CSP (`default-src file: 'unsafe-inline'; ...`) already restricts network-capable directives to `file:`/`data:`/`ws:` and excludes `unsafe-eval`. Settings/shortcuts config loading doesn't do any unsafe object-merge that could enable prototype pollution. IPC handlers in `_boot.js` weren't hardened against malformed input, since `nodeIntegration: true` already gives the renderer unrestricted `require()` access — restricting the IPC surface specifically wouldn't add a real privilege boundary in this architecture.

## 7.2 Known-vulnerable dependencies that could NOT be patched (runtime constraint)

- **`geolite2-redist`** (used for network module GeoIP lookups) and **`pdfjs-dist`**'s fully-patched line both require **Node >=18** starting from their first non-vulnerable major version, and `geolite2-redist@3.x` is additionally **ESM-only**. This Electron 12 app runs on a Node 12-era runtime, so neither can be upgraded without first migrating the whole project to a newer Electron major version — a separate, much larger undertaking than a dependency bump. `geolite2-redist` is left as-is (its `tar`-based critical CVEs require a compromised/MITM'd download source to exploit, since the extracted archive comes from GitHub over HTTPS); `pdfjs-dist` got the workaround described above instead of a version bump.
